חיפוש מתכונים: אפליקציה אמיתית ב-JavaScript

מערכים ואובייקטים map ו-filter DOM ואירועים fetch localStorage

בעמוד הזה נבנה אפליקציה שלמה: חיפוש מתכונים. האפליקציה טוענת מתכונים אמיתיים מהאינטרנט, מציגה אותם בכרטיסים עם תמונה, מאפשרת לחפש ולסנן לפי רמת קושי, ולסמן מתכונים כמועדפים. המועדפים נשמרים בדפדפן גם אחרי רענון.

זה הפרויקט הראשון שלנו שמחבר את כל החלקים: HTML לשלד, CSS לעיצוב, ו-JavaScript שמביאה נתונים, מחליטה מה להציג ובונה את הדף.

חשוב: את אותה אפליקציה נבנה שוב בשיעור 4, ב-React. לכן כדאי לבנות אותה כאן עד הסוף, ולשים לב לדברים שמרגישים מסורבלים: כמה פעמים צריך לחפש אלמנט בדף, כמה פעמים צריך לזכור לקרוא ל-render(), וכמה שורות לוקח ליצור כרטיס אחד. בשיעור הבא נראה איך React פותרת בדיוק את הבעיות האלה.

נבנה את האפליקציה בשלבים. בכל שלב יש עורך עם כל הקוד עד אותו שלב, בשלוש לשוניות: HTML, CSS ו-JS. התוספות של השלב מסומנות בהערה // חדש. לחצו "▶ הרצה" כדי לראות את האפליקציה למעלה ואת הפלט של console.log למטה. כדאי ללחוץ גם "⤢ הרחבה", כדי שהאפליקציה תקבל את כל רוחב העמוד.

👀 לאפליקציה הסופית

מה נתרגל כאן

  • לתכנן אפליקציה לפני שכותבים: מה רואים במסך, ואיך נראים הנתונים
  • לבנות אלמנטים מ-JavaScript עם createElement, ‏textContent ו-append
  • להביא נתונים מ-API עם fetch, ‏async/await, ולטפל בטעינה ובשגיאות
  • להגיב לפעולות של המשתמש: שליחת טופס, בחירה ברשימה ולחיצה על כפתור
  • לעבוד בתבנית state + render: שומרים את המידע במשתנים, ובונים את הדף מחדש לפיהם
  • לעדכן מערכים בלי לשנות אותם (filter ו-...spread), ולשמור אותם ב-localStorage
  • להעלות את האפליקציה לאינטרנט עם GitHub ו-Netlify

בכיתה (כ-15 דק׳ מתוך השיעור): להציג את האפליקציה הסופית, ולבנות יחד את שלבים 2 ו-3 (render מנתונים קבועים, ואז fetch). שאר השלבים לבית. כדאי להשאיר דקה בסוף ל"מה היה מייגע?" (שלב 9) ולכתוב את התשובות על הלוח. בשיעור 4 חוזרים לרשימה הזו ומוחקים ממנה סעיף אחרי סעיף.

‏תוכנית גיבוי: ה-API של dummyjson.com חינמי ובדרך כלל יציב, אבל אם הרשת בכיתה חסומה, שלב 2 עובד בלי אינטרנט (חוץ מהתמונות), ואפשר להמשיך ממנו את ההדגמה של state ו-render.

שלב 0: מתכננים לפני שכותבים

מתכנתים מנוסים לא מתחילים מהמקלדת. לפני שורת הקוד הראשונה עונים על שתי שאלות: מה המשתמש רואה? ואיך נראים הנתונים?

מה רואים במסך

שרטוט מהיר, על דף או בראש, מספיק. מלמעלה למטה:

  1. כותרת: "🍳 חיפוש מתכונים", ובצד השני מונה: "⭐ 2 מועדפים".
  2. שורת חיפוש: שדה טקסט, כפתור "חיפוש", ורשימה נפתחת לרמת קושי.
  3. שורת סטטוס: "טוען מתכונים...", "מציגים 12 מתכונים" או הודעת שגיאה.
  4. רשת של כרטיסים: בכל כרטיס תמונה, שם, שורת פרטים (מטבח · רמת קושי · זמן הכנה), וכפתור "☆ למועדפים".

כל שורה ברשימה הזו תהפוך לאלמנט ב-HTML, וכל דבר שמשתנה בה (המונה, הסטטוס, הכרטיסים) יהיה משהו ש-JavaScript צריכה לעדכן.

איך נראים הנתונים

נשתמש ב-API חינמי בשם DummyJSON, שמחזיר מתכונים לדוגמה (באנגלית). לפני שכותבים קוד, כדאי לראות מה הוא מחזיר. פתחו בלשונית חדשה את הכתובת:

https://dummyjson.com/recipes?limit=1

הדפדפן יציג JSON. הנה החלק שמעניין אותנו, מקוצר:

{
  "recipes": [
    {
      "id": 1,
      "name": "Classic Margherita Pizza",
      "prepTimeMinutes": 20,
      "cookTimeMinutes": 15,
      "difficulty": "Easy",
      "cuisine": "Italian",
      "image": "https://cdn.dummyjson.com/recipe-images/1.webp",
      "rating": 4.6
    }
  ],
  "total": 50,
  "skip": 0,
  "limit": 1
}

מה למדנו מזה:

  • התשובה היא אובייקט, והמתכונים נמצאים בתוך המפתח recipes, שהוא מערך של אובייקטים. כדי להגיע אליהם נכתוב data.recipes.
  • לכל מתכון יש id ייחודי. נשתמש בו כדי לזכור אילו מתכונים במועדפים.
  • הזמן הכולל להכנה הוא prepTimeMinutes + cookTimeMinutes. את זה נחשב בעצמנו.
  • ‏difficulty הוא "Easy" או "Medium". לפי זה נסנן.

הכתובות שנשתמש בהן

מה רוציםכתובת
12 המתכונים הראשוניםhttps://dummyjson.com/recipes?limit=12
חיפוש לפי מילהhttps://dummyjson.com/recipes/search?q=pasta

החלק שאחרי סימן השאלה (?limit=12) נקרא query string. כך שולחים לשרת "פרמטרים", כמו פרמטרים של פונקציה.

מה האפליקציה צריכה לזכור (ה-state)

זו השאלה הכי חשובה בתכנון, והיא תהיה חשובה עוד יותר ב-React. state (מצב) הוא כל מידע שיכול להשתנות בזמן שהאפליקציה רצה, ושמשפיע על מה שרואים:

משתנהמה הוא שומרמתי הוא משתנה
recipesמערך המתכונים שהגיעו מהשרתכשהטעינה מסתיימת
statusהודעת "טוען..." או הודעת שגיאהבתחילת הטעינה ובסופה
difficultyרמת הקושי שנבחרה ברשימהכשהמשתמש בוחר ברשימה
favoritesמערך של ה-id של המתכונים המועדפיםבלחיצה על ⭐

הרעיון המרכזי של הפרויקט: הדף הוא תוצאה של ה-state. בכל פעם שמשהו ב-state משתנה, קוראים לפונקציה אחת, render(), שבונה את הדף מחדש לפי ה-state. ככה אף פעם לא צריך לזכור "איזה חלק בדף צריך לעדכן". זה בדיוק הרעיון ש-React בנויה עליו.

שלב 1: שלד HTML ועיצוב

מתחילים בלי JavaScript בכלל: רק HTML ו-CSS. כתבנו כרטיס אחד ידנית, כדי לראות איך הוא צריך להיראות. בשלב הבא נמחק אותו, ו-JavaScript תייצר כרטיסים כאלה בעצמה.

שימו לב ל-id: לכל אלמנט ש-JavaScript תצטרך למצוא יש id ייחודי: search-form, ‏search-input, ‏status ו-results. עברו גם ללשונית CSS: הרשת של הכרטיסים בנויה עם grid ו-auto-fill, כך שמספר העמודות משתנה לבד לפי רוחב המסך.

נסו: העתיקו את ה-<article> עוד פעמיים בלשונית HTML, ותראו איך הרשת מסדרת את הכרטיסים. עכשיו דמיינו שצריך לכתוב ככה 50 כרטיסים, ולעדכן אותם בכל חיפוש. בשביל זה יש JavaScript.

‏ה-CSS לא ישתנה עד סוף הפרויקט, אז בשלבים הבאים נתמקד בלשונית JS.

שלב 2: JavaScript בונה את הכרטיסים

עכשיו מוחקים את הכרטיס הידני מה-HTML, ונותנים ל-JavaScript לבנות כרטיסים מתוך מערך של אובייקטים. בשלב הזה הנתונים עדיין כתובים בקוד ("hard-coded"): שלושה מתכונים שהעתקנו מה-API. ככה אפשר לבדוק שהבנייה של הכרטיסים עובדת, לפני שמוסיפים את הסיבוך של רשת.

הקוד מחולק לשתי פונקציות, ולכל אחת תפקיד אחד:

  • ‏createCard(recipe) מקבלת אובייקט אחד של מתכון, ומחזירה אלמנט אחד של כרטיס. היא לא מכניסה אותו לדף, רק בונה ומחזירה.
  • ‏render(list) מקבלת מערך של מתכונים, הופכת אותו עם map למערך של כרטיסים, ומחליפה בבת אחת את כל מה שיש בתוך #results.

מה קורה בשורה results.replaceChildren(...cards)?

  1. ‏list.map(createCard) עוברת על כל מתכון במערך, קוראת ל-createCard עם המתכון, ואוספת את מה שחזר. מתקבל מערך חדש: [כרטיס, כרטיס, כרטיס]. שימו לב שכתבנו createCard בלי סוגריים: אנחנו מעבירים את הפונקציה ל-map, ולא קוראים לה בעצמנו.
  2. שלוש הנקודות (...cards) הן spread: הן "פורקות" את המערך לרשימה של ארגומנטים נפרדים. ‏replaceChildren(...cards) זהה ל-replaceChildren(cards[0], cards[1], cards[2]).
  3. ‏replaceChildren מוחקת את כל מה שהיה בתוך #results, ושמה במקום את הכרטיסים החדשים. לכן אפשר לקרוא ל-render שוב ושוב, והכרטיסים לא יוכפלו.

נסו בעצמכם:

  • הוסיפו למערך מתכון רביעי (המציאו אותו, ואפשר להשתמש בתמונה https://cdn.dummyjson.com/recipe-images/4.webp). כמה שורות שיניתם ב-render? אף אחת. זה כל הכוח של הפרדה בין נתונים לבין הקוד שמציג אותם.
  • הוסיפו לכרטיס שורה עם הדירוג (‏rating). צריך להוסיף את השדה לאובייקטים, ליצור עוד אלמנט ב-createCard, ולהוסיף אותו ל-append.

למה לא innerHTML? אפשר היה לכתוב card.innerHTML = `<h3>${recipe.name}</h3>`, וזה נראה קצר יותר. אבל אז הדפדפן מפרש את הטקסט כ-HTML. אם בשם של מתכון יופיע <img src=x onerror="...">, הקוד הזה ירוץ אצל כל מי שפותח את הדף. זו פרצת אבטחה מוכרת בשם XSS. ‏textContent תמיד מתייחס לתוכן כטקסט רגיל, ולכן הוא בטוח. בפרויקט הזה נבנה הכול עם createElement ו-textContent.

כדאי לכתוב את createCard מול הכיתה שורה אחר שורה, ולהריץ אחרי כל אלמנט שנוסף. זו ההזדמנות להראות כמה DOM ידני זה הרבה קוד: 17 שורות בשביל כרטיס של שלושה אלמנטים. בשיעור 4 אותו כרטיס ייכתב ב-JSX בחמש שורות שנראות כמו HTML. לא לגלות את זה עכשיו, רק לשאול: "נוח לכם?"

שלב 3: מביאים מתכונים אמיתיים עם fetch

עכשיו מחליפים את המערך הקבוע בנתונים מהשרת. הפונקציות createCard ו-render נשארות בדיוק אותו דבר. משתנה רק מאיפה מגיע המערך שמעבירים ל-render.

הפונקציה החדשה loadRecipes(url) עושה ארבעה דברים, לפי הסדר:

  1. מציגה "טוען מתכונים..." ומרוקנת את הרשת, כדי שהמשתמש יבין שמשהו קורה.
  2. שולחת בקשה עם await fetch(url), ומחכה לתשובה.
  3. בודקת את res.ok. אם השרת החזיר שגיאה (למשל 404 או 500), זורקת שגיאה בעצמה, כי fetch לא זורקת שגיאה במקרה כזה.
  4. הופכת את התשובה ל-JSON עם await res.json(), ושולחת את data.recipes ל-render.

כל זה בתוך try. אם משהו נכשל בדרך (אין אינטרנט, שגיאה מהשרת, JSON שבור), הקוד קופץ ל-catch, ומציג הודעה ברורה במקום מסך ריק.

נסו לשבור את הקוד בכוונה, כדי לראות שהטיפול בשגיאות עובד:

  • שנו את הכתובת ל-'https://dummyjson.com/recipesXXX'. השרת יחזיר 404, ו-res.ok יהיה false. איזו הודעה מופיעה?
  • שנו את הכתובת ל-'https://no-such-site.example'. הפעם אין בכלל שרת, ו-fetch עצמה זורקת שגיאה. איזו הודעה מופיעה עכשיו?
  • מחקו את המילה await לפני res.json(). מה מודפס בקונסול? (רמז: data הוא עכשיו Promise, ול-Promise אין recipes.)
  • שנו את limit=12 ל-limit=4, ואחר כך ל-limit=30.

שימו לב לסדר: הקריאה loadRecipes(...) בשורה האחרונה מתחילה את הטעינה, אבל לא מחכה לה. הדפדפן ממשיך הלאה, ומציג "טוען מתכונים..." עד שהתשובה מגיעה. ככה הדף לא "קופא" בזמן ההמתנה לשרת. אם עוד לא ברור למה, חזרו לחלק על async ו-fetch.

‏שתי הטעויות הנפוצות בשלב הזה: לשכוח את ה-await לפני res.json() (ואז data.recipes הוא undefined והשגיאה היא Cannot read properties of undefined), ולכתוב render(data) במקום render(data.recipes) (ואז list.map is not a function). כדאי לעשות את שתיהן בכוונה מול הכיתה, ולקרוא יחד את הודעת השגיאה. ‏console.log(data) לפני ה-render הוא הכלי הכי טוב לדבג את זה.

שלב 4: חיפוש עם טופס

הטופס כבר קיים ב-HTML, אבל עוד לא עושה כלום. נאזין לאירוע submit שלו. למה submit של הטופס, ולא click של הכפתור? כי submit קורה גם כשלוחצים על הכפתור וגם כשלוחצים Enter בתוך שדה החיפוש. אנחנו מקבלים את שני המקרים בהאזנה אחת.

מה קורה כשהמשתמש שולח את הטופס:

  1. ‏event.preventDefault(). בלי השורה הזו הדפדפן עושה מה שטפסים עשו מאז שנות ה-90: שולח את הנתונים לשרת וטוען את הדף מחדש. כל מה שהיה ב-JavaScript נמחק.
  2. קוראים את הטקסט מהשדה עם input.value, ומורידים רווחים מההתחלה ומהסוף עם trim().
  3. אם השדה ריק, טוענים שוב את 12 המתכונים הראשונים. אחרת, בונים כתובת חיפוש: /recipes/search?q=....
  4. שולחים את הכתובת ל-loadRecipes. היא כבר יודעת להציג "טוען...", לטפל בשגיאות ולהציג את התוצאות.

תוספת נוספת: אם החיפוש לא מצא כלום, השרת מחזיר מערך ריק, ו-render מציגה עכשיו הודעה "לא נמצאו מתכונים" במקום מסך ריק ומבלבל.

נסו לחפש: pasta, ‏chicken, ‏cake. ואחר כך משהו שלא קיים, כמו zzzz. נסו גם לחפש ואז למחוק את הטקסט ולחפש שוב. האם חוזרים 12 המתכונים הראשונים?

ניסוי חשוב: הוסיפו // בתחילת השורה event.preventDefault(); והריצו. חפשו משהו. מה קרה לתוצאות? (הדף נטען מחדש, וכל ה-JavaScript התחיל מאפס.) החזירו את השורה.

מה זה encodeURIComponent? בכתובת אינטרנט יש תווים עם משמעות מיוחדת: רווח, &, ?, #. אם משתמש יחפש mac & cheese, ה-& ישבור את הכתובת. ‏encodeURIComponent('mac & cheese') מחזירה 'mac%20%26%20cheese', שזה בדיוק אותו טקסט בצורה שבטוח לשים בכתובת. כלל אצבע: כל טקסט שמגיע מהמשתמש ונכנס לכתובת עובר דרך הפונקציה הזו.

הטעות הנפוצה: addEventListener('click', ...) על הכפתור במקום submit על הטופס, ואז Enter לא עובד או טוען את הדף מחדש. שווה לשאול את הכיתה: "איך הייתם רוצים שזה יתנהג כשלוחצים Enter?" ומשם להגיע ל-submit.

שלב 5: סינון לפי קושי, והתבנית state + render

עכשיו נוסיף רשימה נפתחת (<select>) לסינון לפי רמת קושי. השאלה המעניינת היא איך. אפשר לשלוח עוד בקשה לשרת בכל שינוי, אבל אין בזה צורך: המתכונים כבר אצלנו. מספיק לסנן אותם עם filter.

אבל כאן מתגלה בעיה. כרגע המערך של המתכונים לא נשמר בשום מקום: הוא נכנס ל-render ונעלם. כשהמשתמש יבחר "קל", מאיפה נביא את המתכונים כדי לסנן?

הפתרון הוא שינוי קטן בקוד, אבל שינוי גדול בדרך החשיבה. במקום להעביר נתונים ל-render, שומרים את כל מה שהאפליקציה צריכה לזכור במשתנים ברמה העליונה, ה-state:

let recipes = [];       // המתכונים שהגיעו מהשרת
let status = '';        // 'טוען...' או הודעת שגיאה. מחרוזת ריקה = אין הודעה
let difficulty = 'all'; // מה נבחר ברשימה

ומעכשיו יש רק כלל אחד: כל פעם שמשנים משתנה של state, קוראים ל-render(). ‏render לא מקבלת שום דבר. היא קוראת את ה-state, מחליטה מה להציג, ובונה את הדף. בואו נראה את זה בפעולה:

בחרו "קל" ו"בינוני" ברשימה, וצפו בקונסול. שימו לב שלא נשלחת אף בקשה חדשה לשרת: recipes לא משתנה, רק difficulty. נסו גם לחפש chicken ואז לבחור "קל". הסינון עובד גם על תוצאות החיפוש, בלי שכתבנו לזה שום קוד מיוחד.

למה זה טוב יותר?

השוו את loadRecipes לפני ואחרי. קודם היא נגעה בדף בעצמה: כתבה ל-statusEl, ריקנה את results, וקראה ל-render עם נתונים. עכשיו היא רק מעדכנת משתנים. רק פונקציה אחת בכל הקוד נוגעת בדף: render.

בלי state (שלבים 2–4)עם state + render (מעכשיו)
מי משנה את הדף?כל פונקציה, כל אחת חלק אחררק render
הוספת פיצ׳ר חדשצריך לזכור את כל המקומות שצריך לעדכןמוסיפים משתנה, ומשתמשים בו ב-render
"למה הדף מציג X?"צריך לעקוב אחרי כל מה שקרה עד עכשיומסתכלים על ערכי ה-state ועל render

זה React, בלי React. ב-React המשתנים האלה נקראים useState, ו-render היא הקומפוננטה. ההבדל העיקרי: React קוראת ל-render בשבילכם בכל פעם שה-state משתנה. כאן אנחנו צריכים לזכור לעשות את זה בעצמנו. נסו למחוק את השורה render(); מתוך ה-change, ובחרו ברשימה. הקונסול מראה שה-state השתנה, אבל המסך לא. זה הבאג הכי נפוץ בגישה הזו, ו-React פשוט מבטלת אותו.

זה השלב הכי חשוב בפרויקט מבחינה רעיונית, כי הוא הגשר לשיעור 4. כדאי לצייר על הלוח: אירוע → שינוי state → render() → DOM, בחץ אחד שהולך רק לכיוון אחד. ולהדגיש שאף אחד חוץ מ-render לא כותב ל-DOM. בשיעור 4 מציירים את אותו ציור, ומחליפים את render() במילה "React".

שלב 6: מועדפים ⭐

עכשיו נוסיף לכל כרטיס כפתור "למועדפים", ומונה של המועדפים בכותרת. לפי התבנית משלב 5, השאלה הראשונה היא: מה צריך להוסיף ל-state? מספיק מערך של מספרים: ה-id של כל מתכון מועדף.

let favorites = []; // למשל [3, 7] = מתכונים 3 ו-7 במועדפים

למה לשמור רק את ה-id ולא את כל האובייקט? כי ה-id לא משתנה, הוא קצר, וקל לבדוק אותו עם favorites.includes(recipe.id). ויש עוד סיבה, שנראה בשלב 7: קל לשמור אותו בדפדפן.

עדכון בלי לשנות (immutable update)

כשלוחצים על הכפתור, צריך להוסיף את ה-id למערך, או להוציא אותו אם הוא כבר שם. אפשר לעשות את זה עם push ו-splice, שמשנים את המערך הקיים. אבל אנחנו נעשה את זה בדרך אחרת: ניצור מערך חדש ונשים אותו במשתנה.

// להוציא: מערך חדש עם כל ה-id חוץ מזה
favorites = favorites.filter((favId) => favId !== id);

// להוסיף: מערך חדש עם כל מה שהיה, ועוד ה-id בסוף
favorites = [...favorites, id];

זה נראה כמו עבודה מיותרת, אבל זו בדיוק הדרך שבה מעדכנים state ב-React. ב-React, push על מערך של state הוא באג: React משווה את המערך הישן לחדש, רואה שזה אותו מערך, ולא מעדכנת את המסך. אז כדאי להתרגל כבר עכשיו.

לחצו על ☆ בכמה כרטיסים, וצפו במונה ובקונסול. לחצו שוב על אותו כרטיס כדי להוציא אותו. אחר כך חפשו משהו אחר וחזרו (חיפוש ריק). המתכונים שסימנתם עדיין מסומנים, כי favorites לא קשור לחיפוש.

שימו לב לשני פרטים

  • הכפתור לא משנה את עצמו. בלחיצה לא כתבנו favButton.textContent = '⭐ במועדפים'. ‏toggleFavorite רק משנה את ה-state וקוראת ל-render, ו-render בונה את כל הכרטיסים מחדש, כל אחד עם הטקסט הנכון. זו אותה תבנית בדיוק: אירוע → state → render.
  • ‏aria-pressed. המאפיין הזה אומר לקורא מסך (תוכנה שמקריאה את הדף לאנשים עיוורים) שזה כפתור מסוג "מתג", ואם הוא לחוץ עכשיו. ה-CSS משתמש באותו מאפיין כדי לצבוע כפתור לחוץ בכתום: .card .fav[aria-pressed="true"]. ככה מצב אחד משמש גם לנגישות וגם לעיצוב.

יש כאן בעיה: רעננו את העמוד (או לחצו ▶ הרצה שוב). כל המועדפים נעלמו. משתנים ב-JavaScript חיים רק כל עוד הדף פתוח. בשלב הבא נשמור אותם.

שלב 7: שומרים מועדפים ב-localStorage

‏localStorage הוא "מחסן" קטן שכל אתר מקבל בדפדפן. מה ששמים בו נשאר גם אחרי רענון, סגירת הלשונית, ואפילו כיבוי של המחשב. יש לו שלוש פעולות עיקריות:

פעולהמה היא עושה
localStorage.setItem(key, value)שומרת ערך תחת מפתח
localStorage.getItem(key)מחזירה את הערך, או null אם אין כזה מפתח
localStorage.removeItem(key)מוחקת את המפתח

יש מגבלה אחת חשובה: localStorage שומר רק מחרוזות. אם ננסה לשמור את המערך [3, 7] ישירות, נקבל את המחרוזת "3,7", ולא נוכל להחזיר ממנה מערך. לכן ממירים ל-JSON בשמירה, ובחזרה בטעינה:

localStorage.setItem('recipe-finder:favorites', JSON.stringify([3, 7])); // נשמר: "[3,7]"
JSON.parse(localStorage.getItem('recipe-finder:favorites'));            // חוזר: [3, 7]

שימו לב לשם המפתח: 'recipe-finder:favorites' ולא סתם 'favorites'. כל הדפים באותו אתר חולקים את אותו localStorage. אם לשני פרויקטים יהיה מפתח בשם favorites, הם ידרסו זה את זה. כדאי להוסיף לשם המפתח קידומת עם שם האפליקציה. (גם האתר של הקורס שומר כך את הקוד שלכם בעורכים.)

מה משתנה בקוד:

  1. ‏loadFavorites() קוראת את המועדפים פעם אחת, בהתחלה. אם אין כלום שמור, getItem מחזירה null, ו-JSON.parse(null) מחזירה null. האופרטור ?? [] הופך את זה למערך ריק. ואם מישהו שמר שם משהו שבור, ה-try/catch מחזיר מערך ריק במקום שהאפליקציה תקרוס.
  2. ‏saveFavorites() נקראת בכל פעם ש-favorites משתנה, כלומר ב-toggleFavorite.
  3. ‏let favorites = loadFavorites(); במקום [].

סמנו כמה מועדפים, ולחצו ▶ הרצה שוב (או רעננו את כל העמוד). המועדפים נשארו, והקונסול מראה מה נטען מהדפדפן.

רוצים לראות את המחסן עצמו? פתחו את כלי המפתחים (F12), עברו ללשונית Application (ב-Firefox: Storage), ובצד בחרו Local Storage. תמצאו שם את המפתח recipe-finder:favorites עם הערך [1,3] או דומה. אפשר למחוק אותו משם, ולהריץ שוב.

זו האפליקציה המלאה. הקוד בשלב הזה עושה בדיוק מה שעושה האפליקציה הסופית. בקובץ app.js שלה הפונקציות מסודרות לפי נושאים, ויש כמה קיצורים (למשל ? : במקום if), אבל זה אותו קוד. בשלב הבא נעביר אותו לקבצים במחשב שלכם, ונעלה אותו לאינטרנט.

שאלה טובה לכיתה: "למה לא לשמור ב-localStorage גם את recipes?" התשובה: אפשר (זה נקרא cache), אבל אז צריך להחליט מתי הנתונים "ישנים". כלל אצבע: שומרים מה שהמשתמש יצר (מועדפים, הגדרות), ולא מה שאפשר להביא שוב מהשרת.

שלב 9: מה היה מייגע? (ולמה React)

בניתם אפליקציה אמיתית ב-JavaScript "רגילה", מה שנקרא vanilla JavaScript (‏vanilla = "בטעם הבסיסי", בלי ספריות). זה הישג גדול. לפני שממשיכים, עצרו לחמש דקות וחשבו: מה היה מסורבל? איפה הרגשתם שאתם כותבים את אותו דבר שוב ושוב, או שקל לשכוח משהו?

כתבו לעצמכם רשימה, ורק אז השוו לרשימה שלנו:

מה היה מייגע ב-vanilla JSאיך זה ייראה ב-React (שיעור 4)
createCard לוקחת 25 שורות של createElement, ‏className ו-append. קשה לראות מהקוד איך הכרטיס ייראה.כותבים את הכרטיס ב-JSX, תחביר שנראה כמו HTML, ישר בתוך JavaScript.
צריך לזכור לקרוא ל-render() אחרי כל שינוי של state. שוכחים פעם אחת, והמסך לא מתעדכן.‏useState: כשמשנים state, React מציירת מחדש לבד.
render מוחקת ובונה מחדש את כל הכרטיסים, גם כשרק כפתור אחד השתנה. ברשימה של 1,000 מתכונים זה איטי, ותמונות עלולות להבהב.React משווה את הגרסה החדשה לקודמת, ומעדכנת ב-DOM רק מה שבאמת השתנה.
כל הקוד בקובץ אחד, עם משתנים גלובליים. אם נרצה להשתמש בכרטיס במסך אחר, נצטרך להעתיק.קומפוננטות: <RecipeCard />, ‏<SearchForm />. כל חלק בקובץ משלו, ואפשר להשתמש בו בכל מקום.
חמש שורות של querySelector בהתחלה, ו-id שצריך להתאים בדיוק בין ה-HTML ל-JS.אין צורך לחפש אלמנטים. ה-JSX הוא האלמנט, והאירועים כתובים עליו ישירות: onClick={...}.

הנה טעימה. כך תיראה createCard בשיעור 4. אל תנסו להריץ את זה עדיין, רק להשוות:

function RecipeCard({ recipe, isFavorite, onToggle }) {
  return (
    <article className="card">
      <img src={recipe.image} alt={recipe.name} />
      <h3>{recipe.name}</h3>
      <p className="meta">{recipe.cuisine} · {recipe.difficulty} · {recipe.prepTimeMinutes + recipe.cookTimeMinutes} דק׳</p>
      <button className="fav" aria-pressed={isFavorite} onClick={() => onToggle(recipe.id)}>
        {isFavorite ? '⭐ במועדפים' : '☆ למועדפים'}
      </button>
    </article>
  );
}

אותו כרטיס, אותם נתונים, אותו CSS. אבל רואים את המבנה במבט אחד.

ומה לא ישתנה? כמעט כל השאר. ‏fetch, ‏async/await, ‏try/catch, ‏map, ‏filter, ‏...spread, ‏localStorage, וגם הרעיון של state שממנו בונים את המסך. כל מה שכתבתם כאן עובר ל-React כמו שהוא. React לא מחליפה את JavaScript. היא מחליפה רק את החלק שבו אתם בונים את ה-DOM ביד. ומתחת לפני השטח, גם React קוראת ל-createElement ול-append, בדיוק כמו שעשיתם כאן.

לעשות את זה כדיון בכיתה, לא כהרצאה. לבקש מהסטודנטים לקרוא בקול מה היה להם מייגע, ולכתוב על הלוח (או בקובץ משותף). בדרך כלל עולים לבד "יותר מדי createElement" ו"שכחתי render". לשמור את הרשימה: שיעור 4 נפתח בה, ובונים את אותה אפליקציה ב-React תוך מחיקת סעיף אחרי סעיף.

אתגרים

ארבעה אתגרים, מהקל לקשה. כל אחד מהם הוא אפליקציה קטנה בתבנית של הפרויקט: HTML עם id, ‏state במשתנים, ופונקציה שבונה את הדף. כתבו את הקוד, לחצו "▶ הרצה" כדי לנסות בעצמכם, ואז "✓ בדיקה". הבדיקה לוחצת על הכפתורים שלכם ובודקת מה מופיע בדף.

כלל לכל האתגרים: בונים אלמנטים עם createElement ו-textContent, בלי innerHTML. ואם העמוד נתקע (למשל לולאה אינסופית), רעננו אותו. הקוד שלכם נשמר, והוא לא ירוץ שוב עד שתלחצו "▶ הרצה".

אתגר 1: טבלת משתמשים מהשרת קל

ה-API ‏jsonplaceholder.typicode.com/users מחזיר מערך של 10 משתמשים. לכל משתמש יש name, ‏email, ואובייקט address שבתוכו city. פתחו את הכתובת בלשונית חדשה כדי לראות את המבנה.

השלימו את loadUsers, כך שתוסיף ל-tbody#users שורה (tr) לכל משתמש, עם שלושה תאים (td): שם, אימייל ועיר. בסוף הטעינה, הודעת "טוען..." צריכה להיעלם. ואם יש שגיאה, הציגו אותה ב-#status.

רמז: user.address.city. ולשלושה תאים כמעט זהים, לולאת for...of על מערך [user.name, user.email, user.address.city] חוסכת קוד.

אתגר 2: כפתור "טענו עוד" בינוני

הרבה אתרים לא מציגים את כל הרשימה בבת אחת, אלא 5 פריטים, וכפתור "טענו עוד" שמוסיף עוד 5. נבנה את זה עם מערך של 23 פריטים שכבר נמצא בקוד.

ה-state הוא משתנה אחד: shown, כמה פריטים מציגים עכשיו. השלימו:

  • ‏render(): מציגה ב-ul#list את shown הפריטים הראשונים, כל אחד ב-li. רמז: items.slice(0, shown) מחזירה מערך חדש עם הפריטים מהמקום 0 עד (לא כולל) shown.
  • ‏p#counter מציג מציגים 5 מתוך 23. בסוף: מציגים 23 מתוך 23, ולא 25!
  • כשכל הפריטים מוצגים, הכפתור #more צריך להיות לא זמין: more.disabled = true.
  • לחיצה על הכפתור מגדילה את shown ב-PAGE_SIZE, ואז קוראת ל-render().

רמז ל-25: Math.min(shown, items.length) מחזירה את הקטן מבין השניים.

ובעולם האמיתי? כאן כל 23 הפריטים כבר היו בזיכרון, וחילקנו אותם רק בתצוגה. כשיש אלפי פריטים, מבקשים מהשרת רק את החלק הבא. ב-DummyJSON עושים את זה עם ?limit= ו-?skip=: הכתובת https://dummyjson.com/recipes?limit=5&skip=10 מחזירה את מתכונים 11–15. זה רעיון טוב לבונוס בפרויקט.

אתגר 3: חידון בינוני

במערך questions יש שלוש שאלות. לכל שאלה יש טקסט (text), מערך של תשובות אפשריות (options), ו-answer: המיקום (index) של התשובה הנכונה במערך options.

ה-state הוא שני מספרים: current (באיזו שאלה אנחנו) ו-score (כמה תשובות נכונות היו). השלימו את render() ואת choose(index):

  • כל עוד יש שאלות, render מציגה ב-#quiz כותרת h2 עם טקסט השאלה, וכפתור לכל תשובה.
  • לחיצה על כפתור קוראת ל-choose עם ה-index של התשובה. אם היא נכונה, score גדל ב-1. בכל מקרה עוברים לשאלה הבאה, וקוראים ל-render.
  • אחרי השאלה האחרונה, render מציגה סיימתם! ניקוד: 2/3, וכפתור "שחקו שוב" עם id="restart", שמאפס את ה-state.

רמז: map מעבירה לפונקציה גם את ה-index, כפרמטר שני: q.options.map((option, index) => ...).

אתגר 4: סטופר קשה

בנו סטופר שסופר עשיריות שנייה. הפעם אין fetch, אבל יש סוג אחר של קוד אסינכרוני: setInterval(fn, 100) קוראת לפונקציה fn כל 100 מילישניות (עשירית שנייה), ומחזירה מספר מזהה. ‏clearInterval(id) עוצרת אותה.

ה-state: tenths (כמה עשיריות עברו) ו-intervalId (המזהה של הטיימר שרץ, או null אם הוא עצור). דרישות:

  • ‏#display מציג את הזמן בשניות, עם ספרה אחת אחרי הנקודה: 0.0, ‏0.1, ... ‏12.3. רמז: (tenths / 10).toFixed(1).
  • התחל (#start): מפעיל setInterval שבכל פעם מגדיל את tenths ב-1 וקורא ל-render.
  • עצור (#stop): עוצר עם clearInterval, ומחזיר את intervalId ל-null.
  • אפס (#reset): עוצר, ומחזיר את התצוגה ל-0.0.
  • החלק הקשה: לחיצה כפולה על "התחל" לא יכולה ליצור שני טיימרים. אחרת הסטופר ירוץ פי 2 מהר, ו"עצור" יעצור רק אחד מהם. בדקו בתחילת הפונקציה אם כבר יש intervalId.

שימו לב: setInterval לא מדויקת לגמרי. אם הדפדפן עסוק, פעימה יכולה להתאחר, ואחרי דקה הסטופר יפגר בכמה עשיריות. סטופרים אמיתיים שומרים את Date.now() של ההתחלה, ומחשבים את הזמן שעבר מתוכו. זה רעיון טוב לשדרוג.

משימת הגשה: מחפש מוצרים עם עגלת קניות

מה מגישים

אפליקציה שמחפשת מוצרים בחנות, מסננת לפי קטגוריה, ומאפשרת להוסיף מוצרים לעגלה עם סכום כולל. האפליקציה נמצאת בריפו ב-GitHub בשם product-finder, עם index.html, ‏style.css ו-app.js, ומפורסמת ב-Netlify. מגישים שני קישורים: לריפו ולאתר.

זו אותה תבנית כמו בפרויקט, עם נתונים אחרים ופיצ׳ר חדש אחד (העגלה). לפני שמתחילים, עשו את שלב 0: פתחו את הכתובות שבטבלה למטה בדפדפן, ובדקו איך נראים הנתונים. וכתבו לעצמכם טבלת state.

הדרישות

  1. טעינה: בפתיחת הדף נטענים 20 מוצרים, ומוצגים בכרטיסים: תמונה, שם, קטגוריה ומחיר בפורמט $9.99. בזמן הטעינה מופיעה הודעת טעינה, ואם יש שגיאה מופיעה הודעה ברורה (try/catch ו-res.ok).
  2. חיפוש: טופס עם שדה טקסט. שליחה (כפתור או Enter) מחפשת בשרת עם search?q=. חיפוש ריק מחזיר את 20 המוצרים הראשונים. אם אין תוצאות, מופיעה הודעה "לא נמצאו מוצרים".
  3. קטגוריות: רשימה נפתחת (<select>) עם "כל הקטגוריות" ואחריה כל הקטגוריות מה-API. את ה-<option> בונים ב-JavaScript, אחרי שהקטגוריות נטענות. הסינון נעשה בצד הלקוח, עם filter על product.category, בלי בקשה חדשה לשרת.
  4. עגלה: בכל כרטיס כפתור "🛒 הוספה לעגלה", שהופך ל-"✓ בעגלה" כשהמוצר כבר בעגלה. לחיצה נוספת מוציאה אותו. העגלה היא מערך של אובייקטים { id, title, price }. כך אפשר לחשב את הסכום גם כשהמוצר לא מופיע בתוצאות החיפוש הנוכחיות.
  5. סכום: בכותרת מופיע 🛒 3 פריטים · $57.97. את הסכום מחשבים עם reduce, ומציגים עם toFixed(2).
  6. שמירה: העגלה נשמרת ב-localStorage במפתח 'product-finder:cart', ונשארת אחרי רענון.

סיכום שיעור 3

  • מערכים ואובייקטים: כמעט כל נתון באינטרנט הוא מערך של אובייקטים. ‏destructuring ו-spread הם הדרך המודרנית לקרוא ולהעתיק אותם.
  • ‏map, ‏filter ו-reduce: במקום לולאות, מתארים מה רוצים לקבל: מערך מומר, מערך מסונן, או ערך אחד. הן לא משנות את המערך המקורי.
  • ה-DOM: הדף הוא עץ של אובייקטים ש-JavaScript יכולה למצוא, ליצור ולשנות. ‏createElement ו-textContent בונים אלמנטים בבטחה, ו-addEventListener מגיב למשתמש.
  • ‏async ו-fetch: בקשות לשרת לוקחות זמן, ו-await מחכה להן בלי לתקוע את הדף. תמיד בודקים res.ok, ותמיד עוטפים ב-try/catch.
  • state + render: שומרים את כל מה שמשתנה במשתנים, ובונים את הדף מחדש מתוכם אחרי כל שינוי. זה הרעיון המרכזי של React.

בשיעור הבא: React. נבנה מחדש את אותה אפליקציית חיפוש מתכונים, עם אותו API ואותו CSS, ונראה איך כל סעיף ברשימה של "מה היה מייגע" (שלב 9) נעלם. ‏createCard תהפוך לקומפוננטה <RecipeCard />, המשתנים של ה-state יהפכו ל-useState, ואת render() כבר לא נצטרך לזכור לקרוא: React תעשה את זה בשבילנו. שמרו את הקוד של הפרויקט, נשווה אליו.
