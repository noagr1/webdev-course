‏async ו-fetch: נתונים מהרשת

⏱️ 30 דק׳ בכיתה 📚 3–4 שעות לימוד עצמי 🧩 דרישת קדם: חלקים א׳–ג׳ (מערכים, map/filter, DOM)

עד עכשיו כל הנתונים בתוכניות שלנו היו כתובים בתוך הקוד: מערך של מוצרים, רשימה של סטודנטים. אבל באתרים אמיתיים הנתונים נמצאים בשרת: הפוסטים בפייסבוק, מזג האוויר, המוצרים בחנות. הדפדפן צריך לבקש אותם דרך האינטרנט, ולחכות לתשובה.

החלק הזה מלמד שני דברים שהולכים ביחד: איך כותבים קוד שמחכה בלי לתקוע את הדף (קוד אסינכרוני, async/await), ואיך מבקשים נתונים משרת עם fetch. בסוף החלק תמשכו מוצרים אמיתיים מהאינטרנט ותציגו אותם בדף, כולל הודעת "טוען..." והודעת שגיאה.

מטרות החלק

בסוף החלק תדעו:

  • להסביר מה ההבדל בין קוד סינכרוני לקוד אסינכרוני, ולמה הדפדפן צריך את שניהם
  • לחזות באיזה סדר יודפסו שורות כשיש setTimeout בקוד
  • להבין מה זה Promise ובאילו שלושה מצבים הוא יכול להיות
  • לכתוב פונקציות async ולהשתמש ב-await
  • לטפל בשגיאות עם try/catch
  • למשוך נתונים מ-API עם fetch, ולבדוק אם הבקשה הצליחה עם res.ok
  • להציג נתונים מהשרת בדף, עם מצב טעינה ומצב שגיאה
  • לראות את הבקשות בלשונית Network בכלי המפתחים

איך לעבוד עם העמוד: בדוגמאות של החלק הזה יש קוד שמחכה: לטיימר או לתשובה מהשרת. לכן הפלט מופיע קצת אחרי הלחיצה על ▶ הרצה, ולא מיד. זה בדיוק מה שנלמד כאן. הדוגמאות שמושכות נתונים צריכות חיבור לאינטרנט.

סינכרוני ואסינכרוני 5 דק׳

כל הקוד שכתבנו עד עכשיו היה סינכרוני (synchronous): שורה רצה, מסתיימת, ורק אז מתחילה השורה הבאה. כמו תור בסופר: הקופאית מטפלת בלקוח אחד עד הסוף, ורק אז בלקוח הבא.

אנלוגיה: מלצר במסעדה

דמיינו מסעדה עם מלצר אחד. לקוח מזמין פיצה, והכנת הפיצה לוקחת 15 דקות.

מלצר סינכרוני 🐢מלצר אסינכרוני 🚀
מה הוא עושהלוקח הזמנה, הולך למטבח, עומד ומחכה 15 דקות ליד התנור, מגיש, ורק אז ניגש ללקוח הבאלוקח הזמנה, מוסר אותה למטבח, וממשיך לקחת הזמנות משולחנות אחרים. כשהפיצה מוכנה, המטבח קורא לו והוא מגיש
מה קורה לשאר הלקוחותכולם מחכים. אף אחד לא מקבל אפילו מיםכולם מקבלים שירות. אף אחד לא נתקע בגלל הפיצה

בדפדפן, ה"מלצר" הוא JavaScript. יש לו רק "ידיים" אחת: הוא עושה דבר אחד בכל רגע (אומרים ש-JavaScript היא single-threaded). אם הוא יעמוד ויחכה לתשובה מהשרת, הדף כולו ייתקע: אי אפשר יהיה ללחוץ על כפתורים, לגלול או להקליד.

לכן פעולות שלוקחות זמן, כמו בקשה לשרת או טיימר, הן אסינכרוניות (asynchronous): JavaScript "מוסר אותן למטבח" (לדפדפן), ממשיך לרוץ, וכשהתוצאה מוכנה הוא מקבל הודעה וממשיך מהמקום שבו התוצאה נדרשה.

מה לוקח זמן במחשב?

רוב הקוד רץ מהר מאוד: חישוב, השוואה, לולאה על 1,000 פריטים. אלה לוקחים מיליוניות שנייה. אבל יש פעולות שבהן המחשב מחכה למשהו מבחוץ:

  • בקשה לשרת (fetch): התשובה צריכה לעבור באינטרנט, לפעמים מצד שני של העולם
  • טיימר (setTimeout): "תריץ את זה עוד שנייה"
  • פעולה של המשתמש: לחיצה על כפתור. את זה כבר ראיתם בחלק ג׳, עם addEventListener. גם זה קוד שרץ "מתישהו אחר כך"!

‏(5 דק׳) האנלוגיה של המלצר עובדת טוב אם משחקים אותה: לבקש מסטודנט אחד להיות "מלצר סינכרוני" ולעמוד ליד הלוח 10 שניות בזמן שאחרים "מזמינים". הכיתה מרגישה מיד את התקיעה. לציין שהאירועים מחלק ג׳ (addEventListener) הם כבר אסינכרוניים, כך שהרעיון לא חדש לגמרי.

‏setTimeout: הקוד האסינכרוני הראשון 5 דק׳

הדרך הפשוטה ביותר לראות קוד אסינכרוני היא setTimeout. היא מקבלת שני דברים: פונקציה (מה לעשות) ומספר מילישניות (מתי). 1000 מילישניות הן שנייה אחת.

setTimeout(() => {
  console.log('עברה שנייה!');
}, 1000);

שימו לב: הפונקציה שמעבירים היא callback, בדיוק כמו בחלק ב׳ עם map ובחלק ג׳ עם addEventListener. אנחנו לא קוראים לה בעצמנו. אנחנו מוסרים אותה, ומישהו אחר (הדפדפן) יקרא לה כשיגיע הזמן.

הריצו, ושימו לב שהשורה השנייה מופיעה אחרי הפסקה:

חידה: באיזה סדר יודפס?

זו השאלה החשובה ביותר בחלק. לפני שאתם מריצים, כתבו על דף באיזה סדר יופיעו שלוש השורות:

console.log('1: לפני');

setTimeout(() => {
  console.log('2: בתוך setTimeout');
}, 0);

console.log('3: אחרי');

נכון! גם עם 0 מילישניות, הפונקציה של setTimeout לא רצה מיד. היא נכנסת ל"תור" ורצה רק אחרי שכל הקוד הסינכרוני הנוכחי הסתיים. לכן קודם רצים 1 ו-3 (הקוד הרגיל), ורק אז 2. כמו המלצר: גם אם הפיצה מוכנה ברגע שהזמינו אותה, הוא קודם מסיים את מה שהוא עושה עכשיו.

עכשיו הריצו ובדקו את התשובה:

ציר זמן

ככה זה נראה על ציר זמן. JavaScript מריץ את כל השורות מלמעלה למטה. כשsetTimeout נקראת, היא רק רושמת את הפונקציה אצל הדפדפן. רק כש-JavaScript מסיים את הכול ו"פנוי", הדפדפן נותן לו להריץ את הפונקציה שחיכתה:

נסו לשנות: הוסיפו עוד setTimeout עם 500 מילישניות שמדפיס "4", ועוד אחד עם 100 שמדפיס "5". באיזה סדר הם יופיעו? (רמז: לפי הזמן, לא לפי הסדר בקוד.)

🎯 אתגר 1: ספירה לאחור לשיגור קל

כתבו קוד שמדפיס מיד את 3, אחרי שנייה את 2, אחרי שתי שניות את 1, ואחרי שלוש שניות את 🚀 שיגור!. השתמשו ב-setTimeout (כמה פעמים שצריך). כרגע הקוד מדפיס הכול בבת אחת.

למה אי אפשר פשוט "לחכות"? 2 דק׳

אפשר לשאול: למה כל הסיבוך? למה שלא תהיה פקודה wait(3000) שפשוט עוצרת שלוש שניות, וממשיכה?

כי בזמן שהקוד "עוצר", JavaScript תפוס, והוא האחראי על כל הדף. הוא לא יכול להגיב ללחיצות, לעדכן את המסך או לגלול. הדף נראה "קפוא", והדפדפן אפילו עלול להציג הודעה "הדף אינו מגיב". נסו לדמיין אתר שנתקע כל פעם שהוא מחכה לשרת: אחרי כל לחיצה, שנייה או שתיים של קיפאון מוחלט.

לכן ב-JavaScript אין "המתנה שתוקעת". במקום זה אומרים: "כשזה יהיה מוכן, תריץ את הקוד הזה". בהתחלה עשו את זה עם callbacks (כמו ב-setTimeout). היום יש דרך נוחה הרבה יותר: Promise ו-await.

זוכרים את הלולאה האינסופית מחלק ב׳ של שיעור 2? זה בדיוק מה שקורה כש-JavaScript תפוס: הדף כולו נתקע. לולאה שרצה 5 שניות שקולה ל"המתנה" של 5 שניות, ולכן לעולם לא מחכים עם לולאה.

‏Promise: קבלה על הזמנה 5 דק׳

כשמזמינים קפה בדוכן, לא מקבלים קפה מיד. מקבלים קבלה עם מספר. הקבלה היא "הבטחה": "יהיה לך קפה, רק לא עכשיו". עם הקבלה ביד אפשר לשבת, לבדוק את הטלפון, ולחכות שיקראו למספר שלכם.

‏Promise (בעברית: הבטחה) הוא בדיוק הקבלה הזו. זה אובייקט שמייצג תוצאה שעוד לא הגיעה. כש-fetch שולחת בקשה לשרת, היא לא מחזירה את הנתונים (הם עוד לא הגיעו!). היא מחזירה מיד Promise: "הנתונים יגיעו".

שלושת המצבים של Promise

מצבשם באנגליתבדוכן הקפה
⏳ ממתיןpendingהקפה בהכנה. יש לכם קבלה, אבל עדיין אין קפה
✅ הצליחfulfilledקראו למספר שלכם, הנה הקפה. ה-Promise מכיל עכשיו ערך

‏Promise מתחיל תמיד ב-pending, ועובר פעם אחת בלבד לאחד משני המצבים האחרים. אחרי שהוא הצליח או נכשל, הוא לא משתנה יותר.

איך נראה Promise בקוד?

ברוב המקרים לא תיצרו Promise בעצמכם. פונקציות כמו fetch יוצרות אותו בשבילכם. אבל כדי להבין מה קורה, הנה Promise שאנחנו בונים בעצמנו. הוא "מבשל קפה" שנייה אחת, ואז מצליח:

שימו לב למה שהודפס: מה שקיבלנו הוא לא '☕ קפה הפוך', אלא Promise (הקבלה). בקונסול של הדפדפן (F12) תראו אותו כך: Promise {<pending>}, כלומר "הבטחה במצב ממתין". הפלט של העורך באתר מציג אותו בקיצור: Promise {…}. אי אפשר לשתות את הקבלה. צריך לחכות לה. בשביל זה יש שתי דרכים: .then הישנה, ו-await החדשה.

‏.then ו-.catch: הדרך הישנה 3 דק׳

לכל Promise יש פעולה .then(callback): "כשתצליח, תריץ את הפונקציה הזו עם התוצאה". ויש .catch(callback): "אם תיכשל, תריץ את זו עם השגיאה".

נסו לשנות: החליפו את 'אספרסו' ב-'תה' והריצו. עכשיו ה-Promise נכשל, ורצה הפונקציה שב-.catch.

ל-.then אפשר לשרשר עוד .then, וזה יכול להפוך ל"רכבת" ארוכה וקשה לקריאה. לכן היום כותבים כמעט תמיד עם async/await, שנלמד מיד. בכל זאת כדאי להכיר את .then: תפגשו אותו הרבה בקוד ישן, בתיעוד ובדוגמאות באינטרנט.

🤔 פונקציה מחזירה Promise. כמה פעמים הוא יכול לעבור ממצב pending למצב אחר?

  • כמה פעמים שרוצים
  • פעם אחת בלבד: הוא מצליח או נכשל, ונשאר כך
  • פעמיים: פעם מצליח ופעם נכשל
  • אף פעם, Promise תמיד pending

נכון! Promise "מתיישב" פעם אחת. כמו קבלה בדוכן: או שקיבלתם קפה, או שאמרו לכם שאין. ההזמנה לא תחזור להיות "בהכנה".

‏(8 דק׳ ל-Promise ו-.then) אין צורך שהסטודנטים ידעו לכתוב new Promise בעצמם. המטרה היא שיבינו שזו "קבלה" ושיזהו את שלושת המצבים. כדאי להראות בקונסול של הדפדפן fetch('https://dummyjson.com/products/1') בלי await: הדפדפן מציג Promise {<pending>}, וזה הרגע שבו הרעיון "נוחת".

‏async ו-await: הדרך המודרנית 7 דק׳

‏await היא מילה שאומרת: "חכה כאן עד שה-Promise יתיישב, ותן לי את הערך שבתוכו". במקום קבלה, מקבלים את הקפה עצמו. והכי חשוב: הקוד נראה כמו קוד רגיל, שורה אחרי שורה.

יש כלל אחד: מותר להשתמש ב-await רק בתוך פונקציה שמסומנת ב-async. המילה async לפני הפונקציה אומרת ל-JavaScript: "בפונקציה הזו יש המתנות".

השוו את שתי הגרסאות. שתיהן עושות בדיוק אותו דבר:

עם .then (ישן)עם async/await (מודרני)
orderCoffee('אספרסו')
  .then((coffee) => {
    console.log(coffee);
  });
 
async function main() {
  const coffee = await orderCoffee('אספרסו');
  console.log(coffee);
}
main();

הריצו ושימו לב שהשורות מודפסות לפי הסדר, עם הפסקה ביניהן:

אז await כן "תוקע"?

לא! זו הנקודה העדינה. ‏await עוצרת רק את הפונקציה שבה היא נמצאת. כל שאר הקוד, והדף כולו, ממשיכים לרוץ. ‏JavaScript "יוצא" מהפונקציה, עושה דברים אחרים, וחוזר אליה כשה-Promise מוכן. כמו המלצר: הוא "מחכה" לפיצה של שולחן 3, אבל בינתיים מגיש לכל השאר.

למה צריך את main()?

בעורך באתר, וברוב קבצי JavaScript רגילים, אי אפשר לכתוב await ישר בקוד, מחוץ לפונקציה. לכן עוטפים את הקוד בפונקציה async (נהוג לקרוא לה main או loadData), וקוראים לה בשורה האחרונה. אל תשכחו את הקריאה! בלעדיה הפונקציה רק מוגדרת, ושום דבר לא קורה.

לעתיד: בקבצים מסוג module (‏<script type="module">) מותר לכתוב await גם מחוץ לפונקציה. זה נקרא top-level await. נפגוש מודולים בשיעור 4, כשנעבוד עם Vite.

פונקציית async תמיד מחזירה Promise

גם אם כותבים return 5 בתוך פונקציית async, מי שקורא לה מקבל Promise ולא 5. כדי לקבל את ה-5, צריך await גם בצד שקורא:

🎯 אתגר 2: הפונקציה wait בינוני

כתבו פונקציה wait(ms) שמחזירה Promise שמצליח אחרי ms מילישניות (רמז: new Promise ובתוכו setTimeout שקורא ל-resolve). הפונקציה main כבר כתובה ומשתמשת בה: היא אמורה להדפיס "א", לחכות חצי שנייה, להדפיס "ב", לחכות עוד חצי שנייה ולהדפיס "ג".

שגיאות: try, catch ו-finally 4 דק׳

עם .then השתמשנו ב-.catch כדי לטפל בכישלון. עם await משתמשים ב-try/catch. זה מבנה שמתאים לכל קוד, לא רק לקוד אסינכרוני:

try {
  // קוד שעלול להיכשל
} catch (error) {
  // רץ רק אם משהו בתוך try נכשל. error הוא אובייקט השגיאה
} finally {
  // (לא חובה) רץ תמיד בסוף, בהצלחה וגם בכישלון
}

כש-Promise שעושים לו await נכשל (rejected), זה כמו שגיאה שנזרקה באותה שורה: הקוד קופץ ישר ל-catch, והשורות שאחרי ה-await בתוך try לא רצות.

נסו לשנות את 'תה' ל-'אספרסו': עכשיו catch לא רץ, אבל finally כן.

מתי finally שימושי? בדיוק בשביל הודעת "טוען...": מציגים אותה לפני הבקשה, ומסתירים אותה ב-finally, כי צריך להסתיר אותה גם אם הבקשה הצליחה וגם אם נכשלה. נראה את זה בהמשך.

🤔 איפה מותר לכתוב await בעורך באתר?

  • בכל מקום בקוד
  • רק בתוך לולאה
  • רק בתוך פונקציה שמסומנת ב-async
  • רק בתוך try

נכון! await עובד רק בתוך פונקציית async. לכן עוטפים את הקוד ב-async function main() { ... } וקוראים ל-main(). (מחוץ לפונקציה מותר רק במודולים, שנכיר בשיעור 4.)

‏(7 דק׳ ל-async/await) הדוגמה pg-await-order היא המפתח: לשאול את הכיתה לפני ההרצה באיזה סדר יופיעו א, ב, ג. רבים יענו א-ג-ב, כי await "עוצר". ההבנה ש-await עוצרת רק את הפונקציה שלה חשובה מאוד ל-useEffect בשיעור 6. את אתגר 2 אפשר לדלג בכיתה ולהשאיר לבית.

‏fetch: מבקשים נתונים משרת 8 דק׳

עכשיו, כשאנחנו מבינים Promise ו-await, אפשר להגיע לעיקר: לקבל נתונים אמיתיים מהאינטרנט. כל אתר מודרני עושה את זה כל הזמן: רשימת המוצרים בחנות, הודעות בצ׳אט, מזג האוויר. הנתונים לא כתובים בקובץ ה-HTML. הדף מבקש אותם משרת, ומציג אותם כשהם מגיעים.

הפונקציה שעושה את זה נקראת fetch (באנגלית: "להביא"). היא מובנית בדפדפן, ולא צריך להתקין שום דבר.

מה זה API?

‏API (בהקשר שלנו) הוא כתובת באינטרנט שמחזירה נתונים במקום דף HTML. במקום דף מעוצב לבני אדם, מקבלים טקסט בפורמט JSON, שנראה בדיוק כמו אובייקטים ומערכים של JavaScript (פגשנו אותו בחלק א׳). נסו לפתוח את הכתובת הזו בלשונית חדשה בדפדפן:

https://jsonplaceholder.typicode.com/users/1

תראו טקסט שמתחיל ב-{ "id": 1, "name": "Leanne Graham", .... זה משתמש מדומה מתוך JSONPlaceholder, שרת חינמי שנבנה בדיוק בשביל תרגול. בעמוד הזה נשתמש בו ובאתר דומה בשם DummyJSON.

שלושה צעדים

קבלת נתונים עם fetch היא תמיד אותם שלושה צעדים. כדאי לזכור אותם בעל פה:

1️⃣ שולחים בקשהawait fetch(url)←2️⃣ קוראים את הגוף כ-JSONawait res.json()←3️⃣ משתמשים בנתוניםdata.name

כמה דברים חשובים בקוד הזה:

  • ‏יש שני await. הראשון מחכה שתתחיל להגיע תשובה מהשרת (הסטטוס והכותרות). השני מחכה שכל גוף התשובה יגיע ויפוענח. אם הרשת איטית, שניהם לוקחים זמן.
  • ‏res (קיצור של response, תשובה) הוא לא הנתונים. זה אובייקט עם מידע על התשובה: res.status (קוד מספרי, כמו 200), res.ok (האם הצליח), ומתודות לקריאת הגוף.
  • ‏res.json() מחזירה Promise, ולכן צריך עליה await. התוצאה היא אובייקט JavaScript רגיל: אפשר לכתוב user.name ו-user.address.city, בדיוק כמו בחלק א׳.

אין תוצאה? הדוגמאות האלה צריכות חיבור לאינטרנט. אם אתם רואים שגיאה Failed to fetch, בדקו את החיבור ונסו שוב עם ▶ הרצה.

🎯 אתגר 3: הביאו פוסט קל

בכתובת https://jsonplaceholder.typicode.com/posts/1 יש פוסט עם השדות id, ‏title ו-body. השלימו את הקוד: הביאו את הפוסט, והדפיסו את הכותרת שלו בלבד (השדה title).

‏res.ok וקודי סטטוס 5 דק׳

כל תשובה משרת מגיעה עם קוד סטטוס: מספר בן שלוש ספרות שאומר איך הבקשה הסתיימה. לא צריך לזכור את כולם, רק את המשפחות:

קודמשמעותדוגמה
200 (וכל ה-2xx)✅ הצלחההנה המשתמש שביקשתם
404❌ לא נמצאאין משתמש מספר 999
401 / 403🔒 אין הרשאהצריך להתחבר קודם
500 (וכל ה-5xx)💥 תקלה בשרתהבעיה אצלם, לא אצלכם

‏res.ok הוא קיצור נוח: הוא true אם הסטטוס בין 200 ל-299, ו-false אחרת.

המלכודת: fetch לא נכשל על 404

זו טעות שכמעט כל מתחיל עושה. הייתם מצפים שאם המשתמש לא קיים, fetch תיכשל ונגיע ל-catch. אבל לא. מבחינת fetch, השרת ענה, ולכן הבקשה "הצליחה". התשובה פשוט אומרת "לא מצאתי". ‏fetch נכשלת (rejected) רק כשאין תשובה בכלל: אין אינטרנט, כתובת שגויה לגמרי, או חסימת CORS (נסביר בהמשך).

לכן תמיד בודקים את res.ok בעצמנו. אם התשובה לא תקינה, זורקים שגיאה עם throw, וכך היא מגיעה ל-catch כמו כל כישלון אחר:

const res = await fetch(url);
if (!res.ok) {
  throw new Error(`שגיאה מהשרת: ${res.status}`);
}
const data = await res.json();   // מגיעים לכאן רק אם הכול תקין

‏throw (באנגלית: "לזרוק") עוצרת את הפונקציה מיד, וקופצת ל-catch הקרוב. new Error('...') יוצר אובייקט שגיאה עם הודעה, וב-catch קוראים אותה עם error.message.

🎯 אתגר 4: משתמש שלא קיים בינוני

הפונקציה showUser(id) מביאה משתמש ומדפיסה את השם שלו. היא עובדת למשתמש 1, אבל למשתמש 999 היא מדפיסה undefined. תקנו אותה: אם res.ok הוא false, הדפיסו שגיאה: 404 (עם הסטטוס האמיתי מתוך res.status) במקום השם.

הפלט הנכון: Leanne Graham ואחריו שגיאה: 404.

שימו לב שבפתרון יש שתי דרכים נכונות: לזרוק שגיאה ולתפוס אותה ב-catch (כמו בפתרון שלנו), או פשוט if (!res.ok) { console.log(...); return; }. הדרך עם throw עדיפה כשיש כמה דברים שיכולים להיכשל (גם אין אינטרנט וגם 404), כי כולם מגיעים לאותו catch.

מהשרת אל הדף: רשימה ב-DOM 7 דק׳

עד עכשיו הדפסנו לקונסול. אבל המטרה היא להציג את הנתונים בדף. כאן מתחברים שלושה חלקים של השיעור: fetch מביא מערך, מתודות של מערכים (חלק ב׳) עוברות עליו, וה-DOM (חלק ג׳) יוצר אלמנט לכל פריט.

בכתובת הבאה של DummyJSON יש מוצרים של חנות מדומה. limit=5 מבקש רק 5 מוצרים, ו-select=title,price מבקש רק את השדות שאנחנו צריכים:

https://dummyjson.com/products?limit=5&select=title,price

התשובה היא אובייקט, והמערך נמצא בתוכו בשדה products: ‏{ products: [ {...}, {...} ], total: 194, ... }. זה נפוץ מאוד ב-APIs, ולכן תמיד כדאי להדפיס קודם את data ולראות את המבנה שלו.

זה בדיוק הדפוס מחלק ג׳: createElement, ‏textContent, ‏append. ההבדל היחיד הוא שהמערך מגיע מהשרת ולא כתוב בקוד. נסו לשנות את limit=5 ל-limit=10, והרשימה תגדל לבד.

למה textContent ולא innerHTML? הנתונים מגיעים משרת זר. אם מישהו הכניס לשם שם מוצר כמו <img src=x onerror="...">, ‏innerHTML יריץ אותו בדף שלכם. ‏textContent תמיד מציג אותו כטקסט רגיל. לכן: נתונים מבחוץ נכנסים לדף רק עם textContent.

‏React עושה בדיוק את זה בשבילנו: בשיעור 5 נכתוב products.map(p => <li>{p.title}</li>), ו-React ייצור את האלמנטים (וגם יגן עלינו מהבעיה של innerHTML, אוטומטית).

🎯 אתגר 5: כמה משימות הושלמו? בינוני

בכתובת https://jsonplaceholder.typicode.com/todos?userId=1 יש מערך של המשימות של משתמש 1. לכל משימה יש title ו-completed (true או false). הביאו את המערך, ספרו כמה משימות הושלמו, והדפיסו רק את המספר.

רמז: filter מחלק ב׳, ואחריו .length. ‏(הפעם התשובה היא מערך ישר, בלי שדה עוטף.)

מצבי טעינה ושגיאה 6 דק׳

באתר אמיתי, בקשה יכולה לקחת שנייה, שלוש, או להיכשל. אם הדף ריק בזמן הזה, המשתמש לא יודע אם משהו קורה. לכן כל רכיב שמביא נתונים מטפל בשלושה מצבים:

ואת הסתרת "טוען..." שמים ב-finally, כי צריך להסתיר אותה בשני המקרים. הנה התבנית המלאה. כדי לראות את מצב השגיאה, שנו בכתובת את products ל-productz והריצו:

🎯 אתגר 6: ספר מתכונים בינוני

בכתובת https://dummyjson.com/recipes?limit=5&select=name יש 5 מתכונים, בתוך השדה recipes. לכל מתכון יש name. השלימו את loadRecipes:

חיפוש: פרמטרים בכתובת 6 דק׳

שמתם לב לחלק ?limit=5&select=title בכתובות? זה נקרא query string (מחרוזת שאילתה). דרכו מעבירים לשרת פרטים על מה שרוצים:

חלקמה זה
https://dummyjson.com/products/searchהכתובת עצמה (איזה "שירות")
?מכאן מתחילים הפרמטרים
q=phoneפרמטר: שם, ‏=, ערך. כאן: "חפש phone"
&מפריד בין פרמטרים
limit=5פרמטר נוסף: "רק 5 תוצאות"

כל API מחליט בעצמו אילו פרמטרים הוא מכיר. את זה קוראים בתיעוד שלו. למשל, התיעוד של DummyJSON אומר שבכתובת /products/search הפרמטר q הוא מילת החיפוש.

בונים כתובת מקלט של המשתמש

כשהמילה מגיעה מהמשתמש, אסור פשוט להדביק אותה לכתובת: רווח, & או ? בתוך המילה ישברו אותה. הפתרון: encodeURIComponent, שהופכת תווים מיוחדים לצורה בטוחה לכתובת (רווח הופך ל-%20):

const word = 'iphone case';
const url = `https://dummyjson.com/products/search?q=${encodeURIComponent(word)}&limit=5`;
// https://dummyjson.com/products/search?q=iphone%20case&limit=5

טופס חיפוש מלא

הנה הכול ביחד: טופס (מחלק ג׳, עם preventDefault), ‏fetch עם פרמטר, מצב טעינה, ורשימה. כתבו מילה באנגלית (laptop, ‏watch, ‏apple) ולחצו "חיפוש":

נסו לחפש מילה שאין לה תוצאות (למשל zzzz). מה מוצג? איך הייתם משפרים את זה? (רמז: if (data.products.length === 0).)

🤔 ביקשנו משתמש שלא קיים, והשרת החזיר 404. מה קורה בקוד const res = await fetch(url)?

  • ‏fetch זורקת שגיאה ומגיעים ל-catch
  • ‏fetch מצליחה, ו-res.ok הוא false
  • הדף מציג הודעת שגיאה לבד
  • ‏res הוא undefined

נכון! מבחינת fetch השרת ענה, אז ה-Promise מצליח. רק כשאין תשובה בכלל (אין רשת) הוא נכשל. לכן תמיד בודקים if (!res.ok) throw new Error(...).

שליחת נתונים: POST 4 דק׳

עד עכשיו רק ביקשנו נתונים. זו בקשה מסוג GET, ברירת המחדל של fetch. כשרוצים לשלוח משהו לשרת (הרשמה, תגובה, הזמנה), משתמשים בבקשה מסוג POST. לשם כך מעבירים ל-fetch פרמטר שני: אובייקט הגדרות.

  • ‏method: סוג הבקשה. יש גם PUT (עדכון) ו-DELETE (מחיקה).
  • ‏headers: מידע נוסף על הבקשה. כאן אומרים לשרת שהגוף הוא JSON.
  • ‏body: הנתונים עצמם. אי אפשר לשלוח אובייקט ישירות, ולכן הופכים אותו למחרוזת עם JSON.stringify (ההפך של res.json()).

‏JSONPlaceholder הוא שרת לתרגול, ולכן הוא רק מעמיד פנים ששמר: הוא מחזיר את הפוסט עם id: 101, אבל לא באמת שומר אותו. בשרת אמיתי הפוסט היה נשמר במסד נתונים.

כמה בקשות במקביל: Promise.all 3 דק׳

נניח שצריך שלושה משתמשים. אפשר לכתוב שלושה await אחד אחרי השני, אבל אז כל בקשה מחכה שהקודמת תסתיים. אם כל אחת לוקחת חצי שנייה, זה שנייה וחצי. הבקשות לא תלויות זו בזו, אז למה לא לשלוח את כולן בבת אחת?

‏Promise.all מקבלת מערך של Promises, ומחזירה Promise אחד שמצליח כשכולם הצליחו. התוצאה היא מערך של התוצאות, באותו סדר:

שימו לב: ‏getUser(1) בלי await מחזירה Promise, ובדיוק זה מה ש-Promise.all צריכה. אם אחת הבקשות נכשלת, כל ה-Promise.all נכשל, ומגיעים ל-catch.

לראות את הבקשות: לשונית Network 4 דק׳

כשמשהו לא עובד עם fetch, הכלי הכי חשוב הוא לשונית Network בכלי המפתחים. היא מראה כל בקשה שהדף שולח, ומה בדיוק השרת ענה.

  1. פתחו את כלי המפתחים: F12, או Ctrl+Shift+I (ב-Mac: ⌘+⌥+I).
  2. עברו ללשונית Network.
  3. לחצו על הסינון Fetch/XHR, כדי לראות רק בקשות של נתונים (בלי תמונות ופונטים).
  4. גללו לטופס החיפוש למעלה, וחפשו מילה. תופיע שורה חדשה: search?q=....
  5. לחצו על השורה. בלשונית Headers רואים את הכתובת המלאה ואת הסטטוס. בלשונית Response (או Preview, שמציגה אותו יפה) רואים את ה-JSON שהשרת החזיר.
מה רואים ב-Networkמה זה אומר
הבקשה לא מופיעה בכללהקוד לא הגיע ל-fetch. אולי שכחתם לקרוא לפונקציה (main())?
סטטוס 404 באדוםהכתובת לא נכונה. בדקו אותה תו אחר תו
‏(failed) או CORS errorאין תשובה בכלל: בעיית רשת, או שהשרת לא מרשה לאתר שלכם לגשת (ראו CORS למטה)
סטטוס 200, אבל הדף לא מתעדכןהנתונים הגיעו! הבעיה בקוד שמציג אותם. ב-Preview בדקו את המבנה: אולי המערך בתוך שדה כמו products?

להאט את הרשת: בראש לשונית Network יש תפריט שכתוב בו No throttling. בחרו Slow 4G או 3G, והריצו שוב את הדוגמה של מצבי הטעינה. עכשיו תראו את "טוען..." לאורך זמן, כמו שמשתמש עם חיבור איטי רואה. אל תשכחו להחזיר ל-No throttling!

‏(4 דק׳) להדגים את Network על המסך: לפתוח, לסנן Fetch/XHR, לחפש בטופס ולהראות Preview. אחר כך להאט ל-3G ולהריץ את pg-loading, כדי שהכיתה תראה את "טוען..." בעיניים. ההדגמה הזו חוסכת המון שאלות "למה זה לא עובד" בפרויקט.

טעויות נפוצות 5 דק׳

את הטעויות האלה כולם עושים בהתחלה. כדאי להכיר אותן מראש, כדי לזהות אותן מהר.

1. שכחתם await לפני fetch

בלי await, המשתנה מקבל את ה-Promise (הקבלה), ולא את התשובה. לקבלה אין status, ולכן מקבלים undefined. בקונסול של הדפדפן זה נראה כך: Promise {<pending>}. (בעורך באתר: Promise {…}.)

2. שכחתם await לפני res.json()

אותה בעיה בצעד השני: const data = res.json() בלי await נותן Promise, ו-data.name יוצא undefined. כלל אצבע: שני await, אחד ל-fetch ואחד ל-json.

3. משתמשים בנתונים מחוץ לפונקציה, לפני שהגיעו

זו הטעות הכי מבלבלת. הקוד הבא נראה הגיוני, אבל מדפיס undefined:

let user;

async function load() {
  const res = await fetch('https://jsonplaceholder.typicode.com/users/1');
  user = await res.json();
}

load();
console.log(user.name);   // ❌ Cannot read properties of undefined

למה? זוכרים את דוגמת הבישול? load() מתחילה, מגיעה ל-await, ומחזירה שליטה מיד. השורה console.log רצה כשהבקשה עוד בדרך, ו-user עדיין ריק. הפתרון: כל מה שצריך את הנתונים נכתב בתוך הפונקציה, אחרי ה-await (או בפונקציה שנקראת משם).

async function load() {
  const res = await fetch('https://jsonplaceholder.typicode.com/users/1');
  const user = await res.json();
  console.log(user.name);   // ✅ כאן הנתונים כבר הגיעו
  showUser(user);           // ✅ או מעבירים אותם לפונקציה שמציגה
}

4. לא בדקתם את res.ok

ראינו את זה: על 404 fetch לא נכשלת. בלי if (!res.ok) תקבלו undefined מסתורי במקום הודעת שגיאה ברורה.

5. שגיאת CORS

יום אחד תנסו לעשות fetch לאתר כלשהו ותקבלו בקונסול שגיאה אדומה ארוכה עם המילה CORS, ו-Failed to fetch. מה קרה?

‏CORS הוא כלל אבטחה של הדפדפן: דף מאתר אחד לא יכול לקרוא נתונים מאתר אחר, אלא אם האתר האחר מרשה זאת במפורש. ההרשאה מגיעה בכותרת מיוחדת בתשובה (Access-Control-Allow-Origin). למה זה קיים? דמיינו שנכנסתם לאתר זדוני, והוא עושה fetch לאתר הבנק שלכם. הדפדפן שלכם מחובר לבנק, אז הבקשה הייתה מצליחה, והאתר הזדוני היה קורא את היתרה שלכם. ‏CORS מונע את זה.

  • ‏APIs ציבוריים לתרגול (כמו JSONPlaceholder ו-DummyJSON) מרשים לכל אתר, ולכן הם עובדים לנו.
  • אם קיבלתם שגיאת CORS, הבעיה לא בקוד שלכם, ואי אפשר לתקן אותה מהצד של הדפדפן. צריך API אחר, או שרת משלכם שיבקש בשבילכם (על זה בהמשך הקורס).

🤔 מה ידפיס הקוד?
const res = fetch(url); console.log(res.ok);

  • ‏true
  • ‏false
  • ‏undefined
  • שגיאת CORS

נכון! בלי await, ‏res הוא Promise ולא תשובה. ל-Promise אין מאפיין ok, ולכן מקבלים undefined. התיקון: const res = await fetch(url), בתוך פונקציית async.

🤔 קיבלתם שגיאת CORS כשניסיתם לעשות fetch לאתר כלשהו. מה הסיבה הסבירה?

  • שכחתם await
  • שגיאת כתיב בשם המשתנה
  • השרת לא מרשה לאתרים אחרים לקרוא ממנו נתונים
  • האינטרנט איטי מדי

נכון! ‏CORS הוא החלטה של השרת. אם הוא לא שולח את הכותרת שמרשה גישה, הדפדפן חוסם את התשובה. אי אפשר לתקן את זה בקוד של הדף.

‏(5 דק׳) טעות 3 היא החשובה ביותר. כדאי לכתוב אותה על הלוח, לשאול "מה יודפס?", ולחזור לדוגמת הבישול (א-ב-ג). ב-React הבעיה הזו נפתרת בעזרת state: שומרים את הנתונים ב-state, ו-React מצייר מחדש כשהם מגיעים. אפשר לרמוז על כך כבר עכשיו. את CORS מספיק להסביר ברמת "כלל אבטחה של הדפדפן, והשרת מחליט", בלי להיכנס לפרטים.

דף סיכום

// טיימר: מריץ פונקציה פעם אחת, אחרי ms מילישניות
setTimeout(() => console.log('אחרי שנייה'), 1000);

// Promise שמצליח אחרי ms מילישניות
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

// התבנית המלאה של fetch: טעינה, הצלחה, שגיאה
async function main() {
  status.textContent = 'טוען...';
  try {
    const res = await fetch(url);                         // 1. בקשה
    if (!res.ok) throw new Error(`שגיאה: ${res.status}`); //    404 לא זורק לבד!
    const data = await res.json();                        // 2. גוף כ-JSON
    data.items.forEach((item) => { /* createElement */ }); // 3. שימוש בנתונים
  } catch (error) {
    status.textContent = error.message;                   // ❌ אין רשת / 404 / CORS
  } finally {
    // רץ תמיד: מסתירים "טוען..."
  }
}
main();   // לא לשכוח לקרוא לפונקציה!

סיכום

  • קוד אסינכרוני הוא קוד שמחכה למשהו מבחוץ (שרת, טיימר) בלי לתקוע את הדף. JavaScript לא "מחכה": הוא ממשיך, וחוזר לקוד שחיכה כשהתוצאה מגיעה.
  • ‏setTimeout רק רושמת פונקציה לעתיד. הקוד שאחריה רץ מיד, גם עם 0 מילישניות.
  • ‏Promise הוא "קבלה" על תוצאה שעוד לא הגיעה. הוא pending, ואז פעם אחת בלבד fulfilled (עם ערך) או rejected (עם שגיאה).
  • ‏await מחכה ל-Promise ונותן את הערך שבתוכו. מותר רק בתוך פונקציית async, והוא עוצר רק אותה. פונקציית async תמיד מחזירה Promise.
  • ‏try/catch/finally מטפלים בכישלון: catch רץ כשמשהו נכשל, finally רץ תמיד.
  • ‏fetch בשלושה צעדים: await fetch(url), ‏await res.json(), משתמשים ב-data. ‏fetch לא נכשלת על 404, לכן בודקים res.ok.
  • נתונים מהשרת מציגים ב-DOM עם createElement ו-textContent (לא innerHTML), ותמיד מטפלים בשלושה מצבים: טוען, הצלחה, שגיאה.
  • לשונית Network בכלי המפתחים מראה כל בקשה: הכתובת, הסטטוס והתשובה. זה המקום הראשון לבדוק כש-fetch "לא עובד".
